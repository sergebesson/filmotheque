## Options à décider indépendamment

### 1. CI des commandes existantes

#### Décision utilisateur après précision du cadrage

Le 16 novembre 2026, l’utilisateur décide : « Je diffère la CI ; pour mon usage local, les commandes actuelles me suffisent. » Ce choix remplace la recommandation initiale de la retenir sous conditions. Conserver les commandes locales actuelles ; aucune répétition d’installation isolée, injection de faute, création de workflow ou activation GitHub n’est autorisée. Les constats et protocoles ci-dessous sont conservés pour une éventuelle reprise, qui exigera une nouvelle demande explicite.

#### Constats sourcés et bénéfice

- Les [scripts racine](../../../package.json) exécutent le lint serveur/scripts puis client ; `npm test` compile par Vite, puis lance Playwright. `client:install` exécute `npm --prefix www ci`. Les verrous [racine](../../../package-lock.json) et [client](../../../www/package-lock.json) sont au format 3 ; aucune installation unique ne couvre les deux arbres.
- Les deux manifestes et Vite 8.3.8 demandent Node `^20.19.0 || >=22.12.0` ; Playwright verrouillé en 1.65.1 demande Node ≥20. L’environnement observé est Node 24.19.0/npm 11.17.0. Ces versions sont des candidates à fixer, pas une preuve d’installation sur un runner vierge.
- Le [registre versionné](../../../.npmrc) est `https://registry.npmjs.org/`. Tous les champs `resolved` des verrous pointent vers cet hôte (408 racine, 190 client). `@sbesson/configuration-loader` 1.0.4 et `@sbesson/json-db` 1.0.5 ont des URL de tarball npm et une intégrité. Cela n’établit **ni téléchargement anonyme possible aujourd’hui, ni réussite de `npm ci` sans cache ou authentification locale** ; aucun accès aux tarballs n’a été essayé.
- `npm ci` refuse un manifeste incohérent avec le verrou et ne réécrit pas celui-ci [NPM]. Il faut installer les dépendances de développement, garder les mêmes options npm et laisser les scripts nécessaires s’exécuter. Les verrous signalent notamment des scripts pour `@scarf/scarf` et `vue-demi` ; une installation est donc de l’exécution de code tiers, pas une simple lecture. Ne pas ajouter `--ignore-scripts`, `--legacy-peer-deps` ou un contournement sans en examiner les effets.
- Aucun workflow `.github`, `.gitlab-ci*` ou `Jenkinsfile*` versionné trouvé. Le remote est GitHub, mais visibilité du dépôt, offre, budget, branche par défaut, réglages Actions, protections et services externes n’ont pas été inspectés. L’absence de fichier ne prouve pas l’absence de CI externe.
- Le [serveur de test](../../../www/tests/server.cjs) crée films, bases, configuration complémentaire et log dans un répertoire temporaire ; Playwright utilise 4173 et ne réutilise pas de serveur existant. Nuance à conserver : le [chargeur serveur](../../../server/services/load-configuration.js) lit aussi la configuration de base versionnée `data/configuration.json`, ensuite surchargée par la fixture. Les bases/films habituels de `data/` et le serveur 8080 ne doivent pas être utilisés ; promettre « aucune lecture de data/ » serait inexact.
- Le métier testé est local, les tests HTTP/stores/configuration remplacent `fetch`, et les liens externes ne constituent pas un parcours distant validé. Mais [index.html](../../../www/index.html) charge Roboto/Material Icons depuis Google Fonts. Le réseau peut donc influer sur chargement, métriques et assertions visuelles. Aucune exécution réseau coupé n’a été faite ; une suite hermétique n’est pas démontrée.

Le bénéfice est l’automatisation et la détection des dépendances implicites d’une machine de développement, pas une nouvelle couverture fonctionnelle. Les réussites historiques MOD-08 ne prouvent pas la faisabilité de ce job distant.

#### Sous-périmètre minimal recommandé

- GitHub Actions est le candidat naturel vu le remote ; un runner hébergé éphémère Ubuntu 24.04 x64, un seul job, Node 24.19.0/npm 11.17.0 fixés après vérification de leur disponibilité. Pas de runner sur la machine personnelle, de matrice OS/Node, de conteneur supplémentaire ou de service de base de données.
- Séquence à reproduire, **proposée et non exécutée** : `npm ci`, `npm run client:install`, depuis `www` le binaire installé `./node_modules/.bin/playwright install --with-deps chromium`, puis à la racine `npm run lint` et `npm test`. Les bibliothèques système et le navigateur doivent être installés [PW], pas supposés présents. Ne pas définir le chemin `/usr/bin/chromium` propre au runner actuel ; utiliser le Chromium associé au Playwright verrouillé. Pas de `npm start`, ni publication de `www/dist`.
- Garder les deux projets Chromium desktop/mobile et `workers: 1` existants. Pas de retry ajouté pour masquer l’instabilité. Borne initiale proposée : job de 20 minutes, annulation des exécutions obsolètes par branche/PR ; ajuster sur mesures, sans toucher aux délais métier. Les caches ne sont pas nécessaires au premier essai. Un cache npm éventuel devra dépendre des deux verrous, jamais remplacer `npm ci` ; pas de cache `node_modules` ou navigateur par défaut [PW].
- Déclencheurs proposés pour l’activation ultérieure : `pull_request` vers `dev` (opened/synchronize/reopened) et `push` sur `dev` uniquement. Le premier vérifie normalement le résultat de fusion, le second le commit livré [GH-E]. Pas de tags, planification, `pull_request_target`, `workflow_run` privilégié ou événement de déploiement. Ne pas choisir `main` par habitude ; `dev` est ici la référence locale, sa correspondance distante reste à confirmer. `workflow_dispatch` facultatif nécessiterait un fichier sur la branche par défaut [GH-E] : ce n’est pas une activation neutre sur une branche locale.
- Permissions proposées : `contents: read`, aucune autre écriture, aucun secret applicatif/registre, pas d’OIDC ; checkout sans persistance d’identifiants et actions tierces épinglées par SHA à relire. Les scripts d’installation et de test d’une PR restent du code non fiable. Les forks ne reçoivent normalement pas de secrets et leur token est en lecture seule ; appliquer l’approbation des contributeurs externes selon les réglages GitHub [GH-E]. Si l’installation requiert un secret, arrêter ce sous-périmètre et redécider une politique de confiance ; ne jamais basculer sur `pull_request_target` pour contourner le problème.
- Fichiers d’une réalisation éventuelle : un workflow sous `.github/workflows/` et les instructions d’environnement du README. Pas de modification des tests ou de leur configuration dans ce premier lot. Une modification nécessaire révélée par la preuve revient au choix utilisateur.

#### Coûts, diagnostics et limites

La documentation GitHub consultée le 16 novembre 2026 [GH-C] indique la gratuité du calcul standard hébergé pour les dépôts publics ; pour le privé, calcul déduit de l’enveloppe de l’offre puis facturé, stockage d’artefacts distinct. Le tarif de référence Linux x64 2 cœurs est alors 0,006 USD/minute. **Illustration non mesurée :** 100 jobs de 10 minutes représentent 1 000 minutes, soit 6 USD de calcul avant enveloppe incluse, hors stockage et relances. Impossible d’en déduire la facture de ce dépôt sans sa visibilité, son offre, son usage et son budget.

MOD-08 mentionne une suite locale complète de 3,5 minutes : repère historique uniquement, sans installation à froid, pas une prévision CI. Le téléchargement npm/Chromium, l’installation système, les deux événements d’une même évolution et les relances ajoutent durée et coût. Le choix d’un seul job, l’annulation des jobs obsolètes et une rétention courte limitent la consommation. L’auto-hébergement éviterait certains frais fournisseur mais ajouterait maintenance et exposition de la machine ; il est écarté du minimum proposé.

Les journaux d’étapes doivent distinguer installation racine/client, navigateur, lint, build et tests et afficher versions/commit sans variables sensibles. Conserver sur échec `www/test-results/` (traces, captures et captures explicites déjà produites par les tests), avec une rétention proposée de **7 jours**, sans `data/`, configuration personnelle, `.npmrc` utilisateur ni dump d’environnement. La configuration actuelle ne demande pas de rapport HTML : ne pas annoncer un `playwright-report/` disponible par défaut. Les traces peuvent contenir en-têtes Basic Auth et mots de passe de fixture, DOM et réponses ; elles ne sont pas anonymes même sans données réelles. Leur visibilité suit les droits du dépôt et doit être acceptée avant téléversement. Le log serveur temporaire est supprimé à la sortie : pas de promesse de le retrouver sans travail distinct.

#### Expérimentation et critères proposés, à autoriser avant exécution

1. Dans une copie jetable de **l’état local exact**, sans identifiants npm hérités ni caches préremplis, essayer les deux installations verrouillées, puis navigateur/bibliothèques système. Ne pas exécuter `npm ci` dans ce checkout partagé (il remplace `node_modules`), ni y reconstruire le `www/dist` servi par une session habituelle. Ne pas hériter des variables de configuration personnelles (`DB_DIR`, `MOVIES_DIR`, `USER_FILE`, `HOST`, etc.) : le chargeur applique l’environnement après la configuration de fixture. Vérifier accès anonyme aux paquets `@sbesson`, cohérence des verrous, versions et absence de modification des manifestes/verrous. L’accès réseau de cette preuve doit être accepté.
2. Exécuter les commandes existantes sur cet environnement Linux propre : lint puis suite complète ; relever durée par étape, nombre de cas, codes de sortie et artefacts. Garder 4173, les fixtures temporaires et les garde-fous existants ; vérifier l’absence d’écriture dans les bases/films habituels. Documenter la configuration de base lue. Observer les requêtes externes, puis comparer un essai avec polices externes indisponibles si autorisé. En cas d’échec réseau/visuel, ne pas assouplir les assertions : présenter le besoin séparément.
3. Dans cette copie seulement, une faute `no-undef`, puis une assertion Playwright volontairement fausse doivent arrêter la séquence avec un code non nul ; après retrait, la même séquence doit réussir. Cela vérifie la remontée des échecs, pas encore le déclenchement GitHub ni le téléversement distant.
4. Soumettre le workflow exact, événements, permissions, politique forks, budget et rétention. Après autorisation distincte de push/activation et d’une exécution distante, vérifier les vrais événements, l’annulation et l’accès aux diagnostics. Sans cela, ne pas annoncer une CI opérationnelle ni rendre un check obligatoire dans les protections de branche.

**Recommandation initiale : retenir sous ces conditions ; décision utilisateur ultérieure : différer l’option entière.** Si une reprise est demandée, l’installation propre, l’exposition des diagnostics et le budget resteront à accepter avant activation. Aucun accès payant, jeton de registre ou changement d’infrastructure n’est justifié par les seules URL des verrous.

### 2. Maintenance ESLint

#### Constats sourcés et bénéfice avant migration

- Les deux installations verrouillent ESLint 8.57.1 ; racine : `eslint-plugin-node` 11.1.0 ; client : `eslint-plugin-vue` 9.33.0 et `vue-eslint-parser` 9.4.3. Leurs manifestes installés ont été lus, sans les mettre à jour dans le checkout. Le lint actuel a ensuite réussi dans la copie de référence de la preuve ; aucune panne actuelle n’est établie.
- La [politique de support ESLint](https://eslint.org/version-support/) relue en direct annonce ESLint 8 EOL depuis le 5 octobre 2024, ESLint 9 EOL depuis le 6 août 2026 et ESLint 10 comme branche courante [ES-S]. Le motif de maintenance est donc concret, distinct d’un gain de détection automatiquement souhaité. Les versions exactes publiées puis installées dans le banc isolé sont consignées ci-dessous, sans changer les verrous applicatifs.
- Une montée directe avec les plugins inchangés n’est pas étayée : le peer du plugin Vue **installé** s’arrête à `^9.0.0`. Le plugin Node déclare largement `eslint >=5.16.0`, mais sa règle activée `node/no-exports-assign` appelle `context.getScope()` (`node_modules/eslint-plugin-node/lib/rules/no-exports-assign.js:57`), comme `node/no-deprecated-api`. Cette API a été retirée dès ESLint 9 [ES-9]. C’est une incompatibilité de source identifiée, pas le résultat d’un essai de migration exécuté.
- Les guides actuels Vue annoncent la compatibilité ESLint 10 des versions récentes [ES-V]. `eslint-plugin-n` fournit une voie de migration depuis `eslint-plugin-node` et des configs CommonJS [ES-N]. La preuve confirme la disponibilité de n 18.5.0 et ses exigences Node `^20.19.0 || ^22.13.0 || >=24`, ESLint `>=8.57.1` ; Vue 10.12.1/parser 10.4.2 déclarent ESLint 10 compatible. Les peers TypeScript et Stylistic optionnels n’ont pas été installés ; aucun checker de types n’est ajouté par cette preuve.
- ESLint 10 supprime le format eslintrc, change la recherche des configs et refuse les commentaires `eslint-env` [ES-10]. Node 24 observé convient à ses exigences publiées ; Node 22.12 autorisé par les manifestes applicatifs ne suffit pas (22.13 minimum sur cette ligne). Une éventuelle exigence Node 24 pour l’outillage doit être explicite, sans réduire silencieusement le support d’exécution de l’application.

#### Périmètre et politique à conserver

| Frontière actuelle | Contrat de conservation pour une migration |
| --- | --- |
| Racine : `eslint '*.js' 'server/**/*.js' 'scripts/**/*.js'` | Garder cette sélection ; CommonJS/Node, globals Mocha existants, `ecmaVersion: latest`, `eslint:recommended`, règles Node et surcharges explicites de `.eslintrc.js` |
| Client : `eslint . --ext .js,.cjs,.vue`, avec `root: true` | Garder JS/CJS/SFC de `www`, y compris tests et configuration `.eslintrc.cjs` actuellement analysée malgré son nom caché ; ne pas y faire hériter la politique Node de la racine. Le navigateur est l’environnement par défaut ; les globals Node actuellement fournis par `eslint-env node` dans Playwright et les tests Node doivent être reportés sur ces fichiers, pas sur tous les composants |
| Ignorés racine/client et ignorés implicites | Conserver `node_modules`, puis côté client `dist/`, `playwright-report/`, `test-results/`, ainsi que les exclusions implicites utiles (dotfiles). `.eslintignore` n’est plus chargé en flat config et les dotfiles ne sont plus ignorés automatiquement [ES-M]. Ne pas élargir à `.amp`, `www.vue2`, `data`, aux fichiers générés ou à tout le dépôt par un simple `eslint .` racine |
| Sévérités et exceptions | `no-undef` reste bloquant via le recommandé ; `vue/no-mutating-props` reste `error` avec **`shallowOnly: true`** (ne pas interdire soudain les écritures imbriquées autorisées). Conserver les désactivations Vue, les avertissements et les directives locales justifiées. Pas de `--quiet`, de nouveau seuil `--max-warnings`, d’`eslint-disable` de masse ou de reformatage |

La preuve ci-dessous établit désormais l’inventaire moteur : 21 fichiers racine, dont `.eslintrc.js`, et 40 côté client, dont `.eslintrc.cjs`. Les autres fichiers cachés sondés sont exclus. Ne pas confondre `no-undef` en JavaScript et contrôle des types ou des membres de templates : le lint actuel n’est pas un checker de contrats.

Les presets `eslint:recommended` changent entre 8, 9 et 10 (`no-unused-vars`/catch, nouvelles règles, etc.) ; les presets Vue/Node évoluent aussi [ES-9, ES-10, ES-V, ES-N]. Adopter les nouveaux `recommended` sans comparaison changerait la politique. Les anciennes règles `valid-jsdoc`/`require-jsdoc`, explicitement désactivées à la racine, sont supprimées en 9 : retirer ces entrées inactives n’autorise pas l’ajout d’un plugin JSDoc. Pour toute règle active retirée ou modifiée, proposer une équivalence et ses limites ; si impossible, demander une décision avant de la perdre ou de la remplacer. La migration `node/*` vers `n/*` nécessite aussi la correspondance des directives présentes dans les sources, sans toucher leur logique.

#### Sous-périmètre minimal et preuve proposés

**Recommandation initiale : retenir la maintenance à politique constante après preuve isolée.** La preuve est maintenant exécutée ; sa limite sémantique impose l’arbitrage décrit ci-dessous, pas une acceptation implicite. Une simple flat config sur ESLint 8 ne résoudrait pas l’EOL ; ESLint 9 ne doit pas devenir une nouvelle destination pérenne. Le maintien temporaire de 8 reste préférable à une migration qui affaiblit les contrôles ou cache ses différences.

La réalisation éventuelle se limite aux deux configurations ESLint, ignorés, manifestes/verrous des seules dépendances lint nécessaires, instructions d’environnement et adaptations indispensables des commentaires/directives. Garder les deux installations et les deux politiques ; pas de changement `type` racine, de fusion serveur/client, de codemod général, de mise à jour applicative ou de correction des sources pour satisfaire de nouvelles règles. Les noms/formats précis des configs dépendent du couple de versions retenu (notamment plugin n ESM) et seront soumis avec le résultat de la preuve.

Protocole proposé puis **autorisé uniquement en copie isolée** ; résultats et limites d’exécution dans la section suivante :

1. Dans une copie jetable de l’état local, exécuter le lint actuel, enregistrer liste de fichiers, diagnostics et configs résolues sur `index.js`, un service serveur, un store client, `search.vue`, `playwright.config.js` et `tests/server.cjs`. Ajouter des sentinelles temporaires pour vérifier inclusions/exclusions, dont fichiers générés et cachés. Pas de `--fix`.
2. Installer seulement les candidats lint dans cette copie, convertir la configuration et comparer fichiers, globals, options et sévérités effectives. Examiner les écarts de presets **avant** de modifier des règles. Vérifier Node 24 et le Node de l’intégration éditeur ; traiter explicitement le minimum de développement différent de celui d’exécution.
3. Injecter séparément un identifiant non défini côté serveur puis client, une réaffectation directe de prop Vue, et une erreur Node couverte par la règle remplacée. Les deux versions doivent signaler l’erreur au niveau prévu ; une écriture imbriquée de prop autorisée par `shallowOnly` doit le rester. Retirer les fautes, rejouer `npm run lint`, puis `npm test` si des sources/directives ont changé ; aucun changement de logique ou de rendu.
4. Restituer versions exactes, parité obtenue/écarts restants, diff minimal et coût de maintenance supplémentaire. La migration définitive nécessite ensuite un choix explicite. Si conserver la politique nécessite une couche de compatibilité durable ou beaucoup de nouvelles dépendances, revenir à la décision plutôt que l’ajouter d’office.

**Bénéfice attendu au cadrage :** chaîne lint maintenue et configuration explicite. **Limites alors identifiées :** catalogue historique étendu côté serveur, sémantique des règles évolutive et intégration définitive non éprouvée. #### Preuve ESLint locale isolée : résultats du 16 novembre 2026

**Autorisation respectée.** Deux copies indépendantes `before`/`after` de l’état de travail local, sans substitution par `origin/dev`, ont été créées sous `.amp/in/mod10-eslint/`. Leurs `node_modules` applicatifs sont des copies indépendantes des installations locales, sans lien vers celles du checkout. Les candidats lint seuls ont été installés dans un troisième répertoire `tools`, avec versions exactes, fichiers npm utilisateur/global vides distincts, cache propre et registre npm public explicite. Installation réussie : **98 paquets**, scripts de cycle de vie délibérément désactivés pour ce seul banc de lint (`--ignore-scripts --no-audit --no-fund`). Ce choix ne constitue ni une installation applicative propre ni une validation de la CI ; aucun `npm ci` applicatif ou accès aux tarballs `@sbesson` n’a été essayé.

- Référence : ESLint **8.57.1**, plugin Node **11.1.0**, plugin Vue **9.33.0**, parser Vue **9.4.3**.
- Candidat : ESLint **10.15.0**, plugin n **18.5.0**, plugin Vue **10.12.1**, parser Vue **10.4.2**, sous Node **24.19.0**/npm **11.17.0**, Linux x64.
- Les configs flat du banc sont générées **hors des copies**, puis passées explicitement par `--config`/`overrideConfigFile`. Elles reprennent les règles résolues et tables de globals de la référence, plutôt que les nouveaux presets recommandés. Cette extraction est un dispositif de comparaison, pas une architecture ni un fichier de compatibilité proposé à conserver dans l’application.

**Résultats observés :**

1. `npm run lint` réussit dans `before`. Le candidat, appelé avec les mêmes sélections CLI racine puis client et ses configs explicites, réussit aussi après adaptation des seules directives dans `after`. L’API ESLint confirme **21 + 40 fichiers identiques, zéro erreur et zéro avertissement** avant/après. #### Apport attendu au cadrage, avant la preuve

La documentation actuelle explique une intention à la personne qui lit le code ; le typage vérifié compare les utilisations à un contrat formel lors d’une commande locale. On peut conserver les fichiers `.js`, les `<script>` JavaScript et l’Options API : utiliser le moteur TypeScript n’impose pas une conversion des sources en TypeScript. En revanche, il ajoute un outil et une obligation de maintenir les annotations utiles.

Le contrat de recherche envisagé au cadrage est le suivant ; il a ensuite été testé **seulement dans la copie**, pas intégré au checkout [TS-J] :

```js
/**
 * @typedef {object} SearchList
 * @property {{search: string, loading: boolean}} state
 * @property {(search: string) => Promise<void>} setSearch
 */
```

Ce contrat décrit seulement ce dont `search.vue` a besoin. Il ne crée ni store générique, ni schéma de film, ni nouvelle validation à l’exécution. Il faudra relier le type de la prop à ce contrat **et vérifier que le vrai singleton le satisfait** ; une interface inventée côté consommateur et une conversion forcée du store pourraient masquer la divergence qu’on cherche à détecter. Le `@param {string}` de `setSearch` existe déjà : le réutiliser, sans dupliquer la définition de chaque action.

Vite construit l’application mais ne vérifie pas les types [VUE]. Playwright vérifie les comportements effectivement parcourus.
